# MVS Core — improved drop-in source package

Версия пакета подготовлена для отдельного размещения в репозитории MVS как каталог `mvs-core/`.

## Важно: что это за ядро

`mvs-core` — самостоятельный Java/JVM-слой вокруг уже существующего MTProto-движка Telegram. Он предоставляет планирование запросов, ограниченные очереди, таймауты, отмену, безопасные повторы, circuit breaker, bounded frame/reassembly utilities и локальный зашифрованный журнал сообщений.

**Это не самостоятельная реализация MTProto и не замена `ConnectionsManager`.** Шифрование Telegram-трафика, авторизация, реальный выбор физического DC, handshake и сетевой транспорт остаются в существующем движке клиента. `FrameCodec` реализует внутренний формат MVSP и не должен подменять им протокол Telegram или использовать его на Telegram-сокете без отдельной совместимой стороны.

## Состояние интеграции в этом репозитории

Ядро связано со сборкой приложения (ветка `ink-studio`): `include ':mvs-core'` в `settings.gradle`, зависимость в `TMessagesProj/build.gradle`, мост `MtprotoAdapter`/`MvsCoreHost` в исходниках приложения и хук `mvsSetUpdatesObserver` в `ConnectionsManager`.

**Через ядро идёт один реальный запрос клиента:** загрузка `help.getAppConfig` в `MessagesController.appConfigFetcher.getRemote`. Она вызывается при старте и раз в четыре минуты; при ошибке клиент берёт локальную копию из SQLite, поэтому сбой ядра ухудшает конфигурацию приложения, а не ломает клиент.

**Failover по DC реализован в ядре:** `MvsNetCore.sendWithFailover` строит план (домашний DC первым), делает по одной попытке на центр (по умолчанию не больше трёх) и переходит к следующему только на транспортных ошибках — таймаут, `IOException`, отрицательные коды и `0`, 5xx. Ответы 4xx, flood wait и `303 MIGRATE_*` остаются окончательными. План виден через `failoverPlan(preferred)`, здоровье центров пишется в `DcSupervisor`, а в `ConnectionsManager.sendRequest` передаётся конкретный DC.

Границы, без прикрас: физическое соединение, ключи и `MIGRATE_*` остаются в нативном движке; `Config.nativeDcRouting` по-прежнему `false`, и `send()` не меняет выбор DC клиента — центры выбирает только `sendWithFailover`. Остальные запросы приложения идут мимо ядра. Подробности: `android/README.md`.

`adapter-stubs/` нужны только для compile-only проверки контракта; в APK они не попадают.

## Структура

- `src/` — production-код JVM-ядра.
- `test/` — регрессионные проверки без внешних тестовых зависимостей.
- `run-tests.sh` — сборка Java 17 API, запуск тестов и compile-only проверка Android-моста.
- `build.gradle` — опциональный Java-library модуль для Gradle.
- `android/` — адаптер к `ConnectionsManager`, точка входа на аккаунт и инструкция по интеграции.
- `adapter-stubs/` — сигнатурные заглушки для локальной компиляции адаптера; не часть APK.
- `AUDIT.md` — сделанные изменения, результаты и оставшиеся ограничения.

## Локальная проверка

Требуется JDK 17 или новее. Из каталога `mvs-core/`:

```sh
sh run-tests.sh
```

Скрипт компилирует production-код и тесты с `--release 17`, выполняет `RegressionTest`, затем отдельно компилирует `MtprotoAdapter` и `MvsCoreHost` против compile-only заглушек. Временные файлы создаются в системном `/tmp` и удаляются после завершения.

Также можно подключить каталог как Java-модуль Gradle. См. `build.gradle` и `android/README.md`. Само добавление зависимости в клиент в этот архив намеренно не включено.

## Перенос в репозиторий

1. Скопируйте весь каталог `mvs-core/` в корень вашего репозитория.
2. Запустите `cd mvs-core && sh run-tests.sh`.
3. Не копируйте `adapter-stubs/` в Android source set и не применяйте Android-интеграцию, пока не выполните действия из `android/README.md`.
4. После изменения исходников снова запустите тесты и проверьте сборку самого APK.

## Ограничения

- Зелёный JVM-прогон не доказывает совместимость со всеми реальными классами Android-клиента и не является тестом APK.
- Android observer-hook в `ConnectionsManager` в этом пакете не включён в исходники клиента.
- `nativeDcRouting` по умолчанию `false`: ядро не притворяется, что переключает физические DC, когда решение остаётся за нативным движком.
- `CallScheduler.Options.dc` по умолчанию равен `AUTO_DC` (`Integer.MAX_VALUE`), чтобы сохранить выбор DC самим `ConnectionsManager`. Указывайте конкретный DC только когда вызывающая сторона действительно знает нужный DC.
- Для production-хранилища передавайте `AesGcmCipher` ключ, полученный и защищённый через Android Keystore/StrongBox. Не используйте демонстрационный `new byte[32]` как реальный ключ.
- Перед включением реального трафика обязательны сборка `TMessagesProj`, smoke-тест на устройстве и проверка всех жизненных циклов аккаунта.
