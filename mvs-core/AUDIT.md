# mvs-core: состояние после проверки

Ветка `core-audit`, 12.11.2026. Всё ниже — результат прогонов в CI, а не оценка кода.

## Что это

JVM-слой ядра: формат кадра MVSP, планировщик вызовов, ретраи,
предохранитель по DC, журнал сообщений с AES-GCM.

## Как проверялось

CI: `.github/workflows/mvs-core.yml`, `javac` 17 (temurin), шаги с `set -euo pipefail`.

| 43154719776 | 25 PASS / 0 FAIL |

## Ошибки, которые нашёл компилятор

В «исправленных» исходниках части 1, не в тестах:

1. `net/CircuitBreaker.java:52` — `state != CLOSED`. Константа enum вне тела
   enum требует квалификации: `State.CLOSED`. Код не собирался.
2. `net/MvsNetCore.java:37` — фабрика потоков возвращала `Runnable`, а
   `ThreadFactory` требует `Thread`. Код не собирался.
3. `test/.../RegressionTest.java:66` — `sDir`, заглушка вместо каталога.
4. `test/.../RegressionTest.java:105` — `0` в байтовый параметр нужно
   приводить: `(byte) 0`.

## Тесты, которые не могли пройти по построению

- `1b`: `compact(keep=false)` не вызывает `cipher.seal` (ветка `drop` идёт
  через `continue`), поэтому внедрённый сбой не наступал. Заменено на `keep=true`.
- `2c`: после истечения TTL тест подавал фрагмент, который сразу складывается
  в целое сообщение, — `pendingCount` обнулялся. Подаётся неполная сборка.
- `7a`: в исходном виде ничего не enqueue'ил и проверял `got >= 0`.
  Теперь 10 обновлений действительно ставятся в очередь, ожидается ровно 10.

## Чего в модуле нет

- **Мост к движку.** `MtprotoPort` — только интерфейс. Адаптера к
  `ConnectionsManager` нет, поэтому per-DC выбор DC и breaker'ы пока
  статистика, а не управление соединениями.
- **`RequestPipeline`** в документе отсутствует; файл восстановлен по
  сигнатурам вызовов и помечен как реконструкция.
- **`OldRepro`** (набор против старой версии) не запускался: для него нужно
  прежнее дерево, а API несовместимы с исправленным.
- **Нагрузочных тестов нет.** Проверки — точечные, на одном потоке, без
  реального MTProto и без Android.

## Адаптер к движку

Написан против сигнатур, сверенных с этим деревом. Проверено компиляцией только
против стабов: `javac` по `mvs-core/src` + `adapter-stubs` + `MtprotoAdapter` +
`MvsCoreHost`. Авторитетной Android-сборки не было.

| Пункт | Статус | Чем подтверждён |
|---|---|---|
| `sendRequest` 9-аргументный, `datacenterId` доходит до `native_sendRequest` | проверено по исходнику | `ConnectionsManager.java` |
| `onReply` / `onError(code, text, retryAfter)` из `RequestDelegate` | компилируется | прогон 43156645602 |
| `cancel()` -> `cancelRequest(token, true)`, идемпотентно (CAS) | компилируется | прогон 43156645602 |
| `setUpdatesListener` -> hook в двух точках `processUpdates` | hook вставлен, **не компилировался** | нужна Android-сборка |
| Копия `Updates` в `byte[]` до `freeResources` | компилируется | прогон 43156645602 |
| Подключение `:mvs-core` к Gradle | добавлено, **не собиралось** | `settings.gradle`, `build.gradle` |
| Android-сборка `:TMessagesProj` | НЕ запускалась | — |
| Поведение на устройстве | НЕ проверялось | — |

Первый прогон контракта был красным: стаб `FileLog` оказался пакетным, а в дереве
он `public`. То есть контракт ловит расхождения, а не просто зеленеет.

### Что оказалось неверным в прежних формулировках

- «`dc` игнорируется» — неверно: девятиаргументный `sendRequest` передаёт
  `datacenterId` в `native_sendRequest`. Но политику failover всё равно
  определяет нативный движок (7b-c остаётся открытым).
- «подписка на `UpdatesController`» — такого класса в форке нет. Апдейты идут в
  `MessagesController.processUpdates`, поэтому добавлен observer-хук в двух точках.
- Ответ освобождается после возврата из делегата: удерживать `TLObject` нельзя,
  апдейты копируются в `byte[]` синхронно.
- В движке уже есть plugin pre/post-hooks и Ghost Mode — в пайплайне ядра они не
  дублируются.

### Что осталось открытым

- per-DC failover как политика (нужна нативная маршрутизация);
- `OldRepro` не запускался;
- нагрузочных тестов нет;
- перевод трафика приложения на ядро не сделан: `MvsCoreHost` только даёт точку входа.
